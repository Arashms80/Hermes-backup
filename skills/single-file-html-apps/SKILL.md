# Editing single-file HTML apps

Standing preference: the user (Arash) works in Persian. Reply in Persian and keep the app's UI strings Persian/RTL unless he says otherwise.

Second standing preference — legibility of rendered output (result screens, diagrams, printed/PDF pages): **group identical repeated items into one entry carrying its count and index range (`×15 شاخه [1-15]`) instead of drawing each one, and keep prose off the shapes.** Lengths go inside the coloured segments, one marker per special point (weld/joint), at most a single one-line legend for the whole section; no headers, no footnotes, no per-item captions on the artwork itself. He asks for this explicitly — more labels confuse the reader, they do not inform them. **One exception: a one-off dimensioned schematic** (a shop drawing that explains how a *single* piece is cut and joined) where he asks for the numbers on the figure — there the segment lengths, overlap length, hook lengths and the total dimension line DO belong on the drawing; keep the group-and-count rule for repeated identical items only.

Opaque codes are labels too: an internal group id (`و1`) printed on a caption, a table column or a badge means nothing to the reader, so when he says he does not know what it is, **delete it from every surface at once** (screen, canvas, PDF table, legend) rather than from the one he pointed at, and let one visual marker (red underline) plus the single legend carry the meaning.

## When to Use

Use this whenever the deliverable is an edited copy of a browser-run HTML file with no build step: the user pastes a versioned snapshot (`…-v38-….html`) and asks for a change to one screen, controls to be simplified, or an algorithm to be added. The file is a pile of appended `<script>` blocks from earlier rounds of patching, so the work is "add the next layer correctly and prove the old layers did not fight back", not "edit one function".

Skip it for a real repo with modules and tests — use normal codebase tools there.

## Procedure

### 1. Map the file before touching it
- Copy the file into the scratch dir and work on the copy; deliver a new versioned file (`…-v39-….html`), never a silently mutated original.
- Extract every `<script>` block the way the HTML parser does — a block ends at the **first case-insensitive `</script>`**, whatever the JS quoting says — into separate files and run `node --check` on each; record each block's line range and which ones are broken.
- Capture `node --check`'s exit code directly. Piping it (`node --check f | head`) returns the pipe's status, so every block reports OK and you conclude the file is clean when it is not.
- The broken blocks are your baseline: the original's load-time errors must be exactly reproduced by your version — no new ones, no removed ones.

### 2. Find the live code path
- Grep the feature's section markup for element ids, then for the globals its inline handlers call (`cutRun()`, `addCut()`, `cutSectionMode()` …).
- The effective implementation is the **last block that both parses and assigns** that global. Earlier blocks re-wrap the same global (`window.x = wrapped`) and are silently dead if their block has a syntax error — read their source, but do not trust that they run.
- List every init side effect the surviving blocks register (DOMContentLoaded handlers, `setTimeout(..., 400/1200)`, `load` listeners, MutationObservers on feature elements). All of them fire **after** your parse-time code, so they will re-inject the old controls you just removed.

### 3. Make the change as ONE new block appended at the end
- One `<script>` at the end of the body, guarded: `if(window.__X_ON__)return;window.__X_ON__=1;`
- Rebuild the feature's DOM inside that block: capture the nodes worth keeping (kicker/title), wipe the container, re-append, then add your own markup. Guard the build with a flag so later cleanup passes never wipe user-typed values — subsequent passes only purge junk.
- Override **every** global entry point the old blocks and the static markup used (run/calc/mode/toggle/add/print), not just the one you care about; a leftover old alias still reachable from a button defeats the change.
- Purge legacy injected controls from a `JUNK` id list at parse time, at `DOMContentLoaded`, and at ~700/1800 ms timeouts; strip non-`<option>` children from the `<select>` with your own MutationObserver — legacy code appends divs, textareas and buttons *into the select*.
- Never put an id you still depend on in the JUNK list, and assume legacy code may rename a parent node you own.
- **Once a change needs an edit in the *original* file as well as your appended block** (teaching a shared engine a new capability is the usual case), stop hand-editing the deliverable: keep a `build.py` = original + string patches + appended block, and re-run it after every change to your block. Both edits then stay in sync and the build is reproducible from the snapshot the user sent.
- Serve the page and verify (step 4) before reporting; parsing clean is not evidence the UI works.

### 3b. Applying one control design to every screen at once
When the ask is "make add / delete a row look the same in all tabs", do not chase each screen's markup — write ONE normalizer inside your appended block and let the app's own re-renders feed it.

- Walk `document.getElementsByTagName('button')` and rewrite in place: label → `✕`, class → your reference class, `type="button"`, clear the inline cosmetic styles; drop the visual classes (`btn`, `secondary`, `primary`, `danger`) but keep behavioural ones — a handler assigned to the node at creation time still fires after you re-class it.
- Run it debounced off a `MutationObserver` on `document.documentElement` (childList, subtree), plus forced passes at load and ~700/1800 ms: screens build their contents lazily on first visit, so a one-shot pass styles only what existed at load.
- Make it idempotent — skip nodes already carrying your class — or the observer re-fires on its own edits.
- Exclusion guards: skip buttons with inline `position:absolute` (overlay/photo badges lose their geometry), and skip record deletes (`onclick` matching `/\w+Delete\s*\(/`) when the label is `حذف`. A `✕` label means a row delete by convention and may be styled. A missed guard destroys a thumbnail delete button or strips a record card's labelled delete.
- A screen that can add rows but has no delete needs a real handler, not restyling. Rows there are keyed by `_N` ids plus a count in storage: shift values into the lower indices first, remove the **last** row node, then persist the smaller count — remove the clicked row directly and you leave a gap in the ids, and the app's own add path re-renders the deleted row back.
- Prove it with a zero-overlap assertion per row (button rect vs every input rect) plus one real click that shifts values; snippet in the reference.

### 4. Verify in a real browser
Full recipe in `references/browser-verification.md`. Minimum bar:
- Serve over http (`python3 -m http.server <port> --bind 127.0.0.1`) — `file://` is often blocked.
- Fresh load: assert the DOM structure you intended (children order, option list, junk absent, select contains only options).
- Click the **real buttons**, not only the JS functions; cover one normal case with a number you can check by hand, one edge case (empty list, value longer than the stock), and one show/hide round trip.
- Measure layout only after navigating to that tab — inactive screens are `display:none` and every box reports 0×0, which looks like a CSS bug but is not.
- Prove no regressions with an A/B load-error comparison against the original file (snippet in the reference).
- **Stub the expensive side effect before clicking a button that triggers it** — replace the async exporter/renderer with a recorder, click the real button, then assert on the recorded payload (title, section list and kinds, filename, date). That proves the whole button path without running the part that may hang.
- **Distinguish a transient stall from a true wedge before abandoning the session.** After a heavy-calc click the daemon can go unresponsive for a few seconds — even `js('1+1')` times out — yet the same session recovers: wait a few seconds, `ensure_real_tab()`, re-navigate, and the identical click then succeeds. Only when it still never settles is it a real wedge; then start a fresh named session (never retry the dead one) and don't pile up sessions — stop the ones you are done with.
- **Split heavy-click verification into one browser call per click.** A single call that clicks a heavy-calc button, sleeps and evaluates more JS can time out mid-call and lose the whole batch; click in one call, verify the rendered output in the next.
- **Attribute a hang to your change only after running the same call on the untouched original.** If the original hangs identically, say so in the reply and ship a bounded fallback (a timer that falls through to the simple print path) so the user is never left without output.

### 5. Structural consistency across screens (order and grouping)
When the ask is "the tab bar / home grid ordering is a mess, make it logical", find the **three independent orderings** first — the home-grid tiles (their `onclick="go('x')"`), the bottom nav buttons (`data-id`), and the `<section class="screen">` DOM order. In a patch-on-patch app they drift apart because each patching round appended its screen at a different place and the nav `screens`/`navDefs` arrays were never updated in step. Fix with ONE appended normalizer block that reorders all three from a single ordered id list (logical grouping: calculations → estimation → reports/documents → site management → tools); `appendChild` in list order is enough, and run it once at load — nav and tiles are static, sections only need moving once.
- After reordering, click through from the home **tiles** (not just nav buttons) and assert each target section gets `active` — a reordered tile whose `onclick` string survived is fine, but a tile rebuilt without it is not.
- Do not renumber visible MOD badges to match the new order — renumbering decouples the tile labels from every other reference in the app; keep the badges as-is and fix only the physical order.

### 5b. In-app online price refresh (قیمت‌ها)
When the ask is "add a live price update to the app", the refresh must cross-check **at least 3 independent sources** for whatever items have a live feed; three mirrors of one upstream do not count — and must **show the sources**: per-item attribution plus each quote's own date/time, so the user can see how fresh every number is. Construction materials usually have no live feed that answers — keep those rows manual and list the tried sources (with their status) in the sources panel instead of dropping the ask. Manual prices stay the fallback when a source does not answer. Tested endpoints (the tgju **call2** host is CORS-open — fetch it directly; call1 is not), keys, rial→toman units and the proxy routes: `references/iran-market-price-sources.md`. When a refresh reports «چیزی برنمی‌گردونه», curl every wired source with its exact production URL and parse each field against the live text BEFORE touching the app — a stale regex or a symbol the feed no longer carries kills one source while the others still answer; don't guess which one from the app's generic error message.

### 5c. Adding a new screen/tab to the app
When the ask is "add a tab for X", the section markup goes in via the build script (string anchor at the previous section's `</div></section>` or `</main>`), not a hand edit. The nav `navDefs`/`screens` arrays are script-scoped consts — unreachable from an appended block; append the nav button directly at parse time (`b.dataset.id=…; b.onclick=()=>go(…)` — `window.go` and `#nav` already exist because the main script parsed earlier in the document), and add the new id to nav_order.html's ORDER so the normalizer positions it across all three surfaces (the tile regex matches a standard `onclick="go('…')"` home tile). Give the new screen the next MOD badge number; never renumber existing ones.

### 5d. Interactive schematic pan/zoom (in-file SVG)
When a profile/section schematic needs zoom + pan inside a `viewBox` SVG, wire it as a single state object (`VZ={x,y,k}` + `VW/VH`) with `applyZoom()`/`clampPan()`/`zoomAt()`. Bind once: guard the wrapper with `wrap._XBound` so re-renders do not accumulate listeners. Use `pointerdown/move` for mouse drag and separate `touchstart/move/end` for single-finger pan (only when `k>1`) plus two-finger pinch; pinch and drag must not cancel each other — clear `touchDrag` on pinch start and re-seed it when one finger lifts. Wrap `setPointerCapture` in `try/catch`, request `{passive:false}` for drag/pinch `touchmove` and call `preventDefault()` to stop page scroll, and test visibility with `getComputedStyle(el).display` — an empty `style.display` still means `display:none` from CSS.

### 5e. Progressive disclosure for expert-heavy forms (e.g. mix design)
When a calculation form is "too professional" for everyday use, split it into two tiers in the same card: a `mdSimple` form (only the 4–6 fields the user actually varies — e.g. عیار/مقاومت/اسلامپ/حداکثر شن/حجم) always visible, and a `mdAdvanced` form (`display:none` by default) holding the specialist fields (FM, air, densities, absorption/moisture, prices, `f'cr` mode). Add two buttons at the top: `⚡ انتخاب خودکار مقادیر عرف` fills every advanced field with the market-conventional defaults (e.g. ACI 211.1 defaults for Iran: FM 2.7, شکسته، هوا ۰، Gc 3150/Ga 2650/Gb 1600، جذب ۱٪، رطوبت ۰٪) but never overwrites simple fields that already have a value — check `String(el.value).trim()` before filling; and `🔧 تنظیمات تخصصی` toggles the advanced tier and its hint banner (`حالت ساده فعال است…`) with text swap to `بستن تنظیمات تخصصی`. Wire `disabled` linkage (e.g. S input) after preset as well.

### 5f. Input ergonomics polish (placeholder + thousands + derived remaining)
When placeholders like "مثلاً ..." compete visually with real values, restyle with `html input::placeholder` (and textarea) at low opacity/weight and small size (`opacity:.72`, `color:#9aa8ba`, `font-size:.84em`; dark `#63788f`) placed as the very last `<style>` block so it wins over legacy `!important` ID-scoped rules; inject via `build.py` at `rfind('</body>')`. For large monetary/quantity fields, switch `type=number` → `type=text` + `inputmode=decimal`, normalize Persian/Arabic digits (`۰-۹/٠-٩/٫٬،`), install a raw `value` getter (`Object.defineProperty` returning ungrouped digits) so existing `+el.value`/`parseFloat` call sites keep working, format the visible `VAL.set` with `group(intPart)` on every `input` while preserving caret via significant-char counting, and scan lazily (focusin + MutationObserver + timed rescans). A read-only derived field such as `باقیمانده = تنخواه − جمع هزینه` stays `readOnly` with `placeholder="خودکار"`, recomputes on `input` of either source, colors negative (`#ff6b6b`), and is re-wrapped after programmatic loads (`loadDaily` etc.) via a post-wrap with `setTimeout`.

### 5g. Global PDF air pass — one string-patch set for all outputs
When every PDF (branded `acBrandedPdf` + daily `printDailyInner`) is asked to become "خلوت/شفاف/مرتب" (uniform frame/row/font/alignment), do NOT edit screens one-by-one — the branded engine feeds attendance/materials/expenses/mix-design/cut-shop and daily is separate, so a single `build.py` string-patch set must hit both: thin outer frame (`#dde4ee 1.3px`), lighter palette (`line #e6ebf0`, `soft #f8fafb`, `muted #6b7a8a`), smaller label/value fonts (`12→11`, `13→12.5`, `12→11.5`), taller rows with larger line-height (`34→38`, `40→44`, `1.35→1.45`), subtle zebra (`#f9fbfd`) and thin row strokes (`#eef2f6 0.8`), shorter table header (`38→36`) with navy underline, and lighter footer/notes cards (`#fffaf0/#f0d9b0`); verify with marker counts (`dde4ee` present, `cbd3da` zero) across the built file.

### 5h. Turning a weak calculator into a takeoff/order list + a cut-and-bend shop drawing
When he calls a calculation screen «کم‌کاربرد و بی‌فایده» and offers to delete it, do NOT delete it: answer with 2–3 concrete upgrade options (light polish / full upgrade / delete) plus your recommendation, then build the one he picks — he often takes the full upgrade, but a delivered upgrade can still be rejected afterward («خیلی کاربردی نیست»): when he then says delete, remove the whole screen immediately per 5i without re-offering options — one offer per decision. The full upgrade converts a bare `وزن = W(d²)×طول×تعداد` widget into a takeoff: per row قطر + تعداد + طول خالص + **«خم روی چند سر؟»** (بدون خم / یک سر / دو سر / سه سر / چهار سر) + نوع خم/قلاب + وصله, with the hook length taken from the app's own `PC.bendLen` multiplied by the number of bent ends, the lap from `PC.ldStraightM9`, prices auto-read from the price tab **with a graceful fallback** (no price saved → drop the money column, keep the whole takeoff working), and the outputs: تفکیک سفارش per diameter (شاخهٔ stock / طول / وزن / ton / مبلغ), PDF + Excel, and a hand-off that pushes the computed rows into the cut-optimizer tab and switches its section to rebar.

Shop drawing per row — he wants the dimensions ON the figure:
- Split the cut length into market-stock pieces with overlaps: `k = ceil((total − lap) / (stock − lap))`, last piece `= total − (k−1)(stock − lap)`; `lap = 0` means plain butt-jointed pieces (draw no overlap band). Formulas, per-end hook distribution, the SVG scaffold and the order-text template: `references/rebar-takeoff-and-shop-drawing.md`.
- The SVG carries one coloured segment per piece with its length above it, the overlap band (dashed `#f47b20` at 0.28 alpha) with its length below, hook glyphs + hook length on the free ends only, and a total dimension line under the bar.
- Below the figure, a numbered **دستور قطع و خم** in plain language ("شاخهٔ ۱۲متری را قطع کن → قطعهٔ ۱ … و سر آن را … خم بزن"، "هر قطعه را به اندازهٔ … روی قبلی اورلپ کن و ببند") — the figure shows geometry, the list states the actions.
- PDF: teach the branded engine the two section kinds you reuse for this — `kind:'image'` (render each schematic SVG to an offscreen canvas → `{src, caption}`) and `kind:'list'` for the order text; see the `image` preload pitfall below.

### 5i. Removing a screen/tab cleanly
When he says delete a whole screen, remove EVERY surface in one `build.py` edit and rebuild — a half removal leaves nav items and buttons pointing at a missing section:
- Remove: the `<section id="x">` block; the feature's JS engine (find BOTH the original marker-comment block AND any appended/v2 replacement — grep the marker comment and the new global names separately); the home tile (`<button class="tile" onclick="go('x')"`…`</button>`); the navDefs item; the id from `screens` and the ORDER / nav-grouping (G) arrays; the module's entry in the report-module list and its formula-map line; and snapshot/snapContext keys — empty the value, keep the key, so report code reading it gets `[]` not `undefined`.
- Leave other modules' internal usage of the same word alone (a cut-optimizer section value, a data-table row key, a checklist figure id) — those are independent features that still work.
- Verify on the built file: the section id, tile onclick, engine marker and new global names must grep to zero; every script block still passes `node --check`; the nav array's item after the removed one flows correctly (a bad removal regex leaves the build exiting "not removed (expected 1)").
- Keep the removed feature's source files on disk but unused by the build, so a later re-add is a one-line change.

### 5j. Auditing an in-app engineering formula against its standard
When he says "check every formula in <screen> against the latest internal and external revision" and mentions one number that was wrong, do NOT fix that number — a plausible-looking constant table is the usual culprit and his example is one symptom of a table that was never sourced. Audit the whole chain and report a defect list with the governing clause for each fix.

- Fetch the standard's own text (the ACI 211.1 PDF extracts cleanly from a university mirror) — not a third-party blog table, not engineering memory; both are wrong, in different cells.
- Inventory every constant in the engine and diff it against the standard one table at a time: strength↔w/c curve, unit water, coarse-aggregate volume factor, f'cr rule, durability limits (max w/c / min cement / min f'c / air), density-absorption-moisture defaults.
- Round-trip one known cell per table through the unit conversion (1 lb/yd³ = 0.5933 kg/m³) instead of trusting a converted table wholesale.
- Read the table **footnotes** — they carry the binding corrections (which exposure basis a water column assumes, rounded vs crushed aggregate, water-reducer credit, the last slump column).
- Check volume bookkeeping: the absolute-volume sum must carry entrapped air for the aggregate size even with no air entrainer, or the deficit lands in the fine aggregate and the sand is overstated.
- Recompute one worked example per branch by hand (and against the standard's own worked example) before saying "formulas checked"; name what you did not audit as an open item rather than silently rewriting it.

Digitized ACI 211.1 / ACI 318 tables, anchor pairs, unit constants and the app-vs-standard defect list: `references/concrete-mix-design-aci.md`.

### 6. Report
State what changed, what was verified with the real numbers the browser returned, and what was deliberately left alone (with the reason).

## Pitfalls
- **Never emit a literal `</script>` inside a JS string** (print/export helpers that embed an HTML document are the usual trap). The HTML parser terminates the element at the first `</script>` regardless of quoting, so the whole block becomes one unterminated string and never executes — the only symptom is a single console SyntaxError, and the feature silently stays on its old code.
- **Do not repair dead legacy blocks when reviving them would re-add the clutter the user asked you to remove** (duplicate checkboxes, floating patch badges, extra fields). Leave them dead, verify the error baseline is unchanged, and say so in the reply.
- **An ambiguous field name in the request gets the most useful reading, an explicit label, and a flagged interpretation in the reply** — implement it, then tell the user which reading you chose so they can correct it in one line instead of debugging your guess.
- **Old blocks keep mutating the DOM after your build** (DOMContentLoaded injection, delayed timeouts). A one-shot rebuild at parse time is not enough; schedule the same purge on those later ticks.
- **Output that can be printed needs a standalone print path, and if the app already has a branded report engine, route the new output through it** (new section kinds are taught by patching its section-dispatch with a string anchor via the build script) so header, footer, spacing and signature lines match every other output the app produces. Guard that path with a timeout that falls back to the plain print window, and give the fallback its own CSS — it inherits none of the page's.
- **Grouping repeated output must come from one signature helper used by every surface** — screen list, PDF images and PDF table all derive their groups from it, so the counts and index ranges cannot drift between them; verify all three together, and expect image/table row counts to equal the number of distinct signatures, not the raw item count.
- **`pkill -f <pattern>` can kill your own shell**: the pattern also matches the command line of the `pkill` you just typed. Spell it with a character class (`chrome[-]headless`, `browser[_]harness`) so only the target matches.
- **Long-lived helper servers die between sessions**: restart the http server with `background=true` and re-check with curl (`HTTP 200`) before any browser verification — a `chrome-error://` page or an empty `body` after navigation usually means the server is down, not that the app broke.
- **Never confirm exact UI text from a screenshot** — vision reads of Persian/RTL strings and digits are unreliable. Take exact strings from `textContent`; use screenshots only for layout, overlap and hierarchy.
- **A test that measures DOM geometry while the screen is hidden reports zeros** — navigate to the tab first, then measure.
- **Your new class can lose to a screen-scoped `!important`** (`#screen .subcard button{min-height:43px!important}`): among `!important` declarations specificity still decides, so read `getComputedStyle` width/height/border-radius back after restyling and, when wrong, add an ID-scoped `!important` of your own. Asserting only the class name passes while the rendered control is the wrong size.
- **A build anchor like `</body>` can be a trap: the FIRST occurrence may live inside a dead print block's HTML string** — insert at `out.rfind('</body>')` (the real document end) or your appended block lands inside a string in a print template and never runs.
- **A secret-scan layer can redact a literal storage-key string out of your written file** (`LS_KEY='BEAMETS_PRICES_V1'` → `LS_KEY='***'` on disk, silently, while your tool call looked correct). Build localStorage keys from concatenation (`'BEAMETS'+'_PRICES_'+'V1'`) so no literal matches the scan, and verify the on-disk pattern after writing.
- **The nav-order normalizer runs before an appended tab-build block** — the new tab/tile/section must re-run the same ORDER sort itself (nav buttons, home tiles AND sections), or it lands last on every surface.
- **Only `window.*` assignments cross `<script>` blocks** — a `const X` engine object declared in one block is invisible to a later appended block (`window.X` is undefined there). Bridge it with the build script: inject `window.__X__=X` at a marker right after the engine's block ends and read `window.__X__||window.X` from the appended block. Asserting `!!window.X` in a page whose engine visibly works is not evidence your block can see it.
- **Never wrap a global the app assigns inside a `DOMContentLoaded` listener** — at your appended block's parse time it is still `undefined`, so the `typeof window.go==='function'` guard is false and the wrapper silently never installs. Hook the user event instead: a capture-phase click listener on the nav buttons plus a small `setTimeout` for the post-render work.
- **A derived widget (cost chart, summary) must be wired into every render path** — hook each output container with a `MutationObserver` (childList + subtree; full `innerHTML` swaps replace the table) AND inject directly after each heavy action as a backup, both with the same idempotency check. Require the data before inserting: accept only rendered rows whose cost column parses to a number and demand ≥2 items — a text column in the same position (notes) otherwise feeds the chart garbage.
- **Placeholder styling loses to legacy `!important` unless it is `html`-prefixed and injected last** — a mid-file rule is overridden; place it in the final appended block at `rfind('</body>')` and verify `getComputedStyle` on a real input.
- **Thousands grouping breaks every existing calculation if you mutate `el.value` without a raw getter** — `type=number` cannot show commas, so convert to `text` and expose the ungrouped value through a `value` getter; normalize `۰۱۲۳۴۵۶۷۸۹/٠١٢٣٤٥٦٧٨٩/٫٬،` before parsing and keep caret position, otherwise `+el.value` reads `NaN` and totals collapse.
- **A global PDF polish that patches only `acBrandedPdf` leaves the daily report mismatched** — patch both engines in `build.py` (the same palette/frame/row constants appear in each) and assert zero remnants of the old border color.
- **A constant table that a code does not define is the tell that its values were invented** — a w/c↔strength table split into crushed/round columns when the standard gives one curve per air condition, or a durability limit with no clause behind it. On that signal distrust and re-source the whole table, not just the cell the user quoted.
- **A code rule that is the max/combination of several expressions must never be implemented as a single term** — `f'cr = f'c + 1.96·s` looks code-shaped but matches no ACI criterion (the SD case is the greater of two expressions); read the clause, not the shape of the formula.
- **Derive self-test reference values from the app's own formula source, not from engineering memory** — unit conventions per field (wall dimensions in meters, block dims in mm), rounding and the result's shape live in the code. Read the function first, compute the expected number from ITS conventions, and print the returned object's full keys before asserting a field exists (a `total` you assumed may be named `mm`).
- **Teaching the PDF engine a new image-carrying section kind is only half the job** — the engine preloads `it.src → it._img` for `kind==='photos'` only while the `image` branch filters on `it._img`, so a section you add without widening the preload condition renders empty (its own placeholder text) and the drawings vanish with no error. Patch the preload condition in `build.py` and assert the marker.
- **Strip the `<script>`/`</script>` tags from a block file saved as a complete script element before injecting it inside an existing script block** — a nested `<script>` is a parse error that breaks the block-splitting contract; do it with a regex in `build.py`, and keep the block file itself usable standalone.
- **Helpers inside your appended IIFE are invisible to node harnesses** — `typeof` checks pass, the page works, and the harness dies with `ReferenceError: <fn> is not defined`. Expose the pure ones on a single accessor (`window.__X_TEST__={split,svg,order,…}`) and call them through it in tests.
- **A fake-DOM harness must stub canvas/Image/Blob/URL and override the row-list query** once the code under test draws to an offscreen canvas: a generic `createElement` stub has no `getContext`/`toDataURL`, so the render path throws inside its own `try{}` and the section silently disappears; and `container.querySelectorAll('.row')` must return the rows you registered, or the calc runs on an empty list and reports "ردیفی ثبت نشده".
- **Adding PDF sections on purpose invalidates an old exact-count assertion** — assert on membership (`sections.some(s=>s.kind==='image')`) rather than a hard length, or every deliberate section addition reads as a regression.
- **Build a large appended block with a sequence of `patch` calls against a skeleton, not one giant `write_file`** — a single very large write can land truncated or mangled through context handling, and the only symptom is a zero marker count on a function you definitely wrote.
- **Write an edit/removal regex from the BUILT artifact's bytes, not from the Python source's JS string literal or from `repr()` output** — the same array literal can be escaped inside `build.py` (`\'rebar\'`, because it sits in a JS string) while the emitted file carries plain quotes (`['rebar','…','<svg …'],`), so a pattern copied from the source matches nothing and the build dies with "not removed (expected 1)". Grep the built file for the literal, print `hex(ord(ch))` for a few characters at the hit, and anchor the pattern on that: e.g. `re.compile(r"\['rebar','[^']*','<svg class=\"section-svg\".*?'\],", re.S)`, then assert `count==1`.
